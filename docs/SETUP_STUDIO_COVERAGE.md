## Reading the catalogue

Twelve areas are destinations, not ordered completion steps. `settings` and `templates` identify real controls inside the linked workspace; links generally open the workspace landing screen, so the manual tab is specified below. `operations` identifies transactions or evidence, not a reusable settings form. `embedded` references existing Setup tabs; integration and their editor guards are a separate task. No catalogue function reads configuration or saves data.

`available` means navigation is permitted by the catalogue checks. It does **not** grant editing, assert configured status, or bypass the route wrapper, editor, role, company, feature, or server checks. Required permissions use **any-of** semantics: canonical navigation metadata for module routes, actual SetupPage tab permission branches for embedded Setup destinations. The actual module catalogue also gates paths without a feature key. While it loads, availability is `checking`; fetch failure is `unknown`, not disabled. Known disabled keys or path ownership return `unavailable`; known permission/scope denials return `restricted` first.

Scope describes records, not the company banner: `company` is company/employee-owned; `tenant` is shared tenant configuration; `mixed` combines shared definitions with company or employee records, or explicitly supports nullable company scope. Company-scoped group accounts retain the current embedded-tab allowlist: companies, branches, cost centers, GL/rates and administrative audit. Tenant-only destinations are restricted in that context. Mixed routes retain their canonical per-record checks; the catalogue cannot certify their editors.

All destinations except onboarding have `assistance: not-connected`. This means no area-to-existing-form document adapter is established here, even when legacy Setup AI can propose related settings. Onboarding's `existing-onboarding` records the existing browser draft transfer into `OnboardingTab`; it is not new extraction or publication. Original source and form draft storage, target validation, and save verification remain in the existing workflow.

The `/setup` route wrapper admits more permission keys than any individual tab. Embedded catalogue destinations therefore mirror `SetupPage` tab permission branches: `organization.write` or `organization.establishment.write` opens its existing writable tab set; Companies additionally admits `organization.read`; Statutory Rules additionally admits `payroll.rates.read`. A company reader does not gain unrelated tabs; a rates reader does not gain company or organization settings. `payroll.rates.statutory_override` alone does not open a tab. Company-scoped group restrictions are then applied unchanged. These are navigation checks: statutory-reader role checks and all narrower editor write checks remain mandatory in Task 3 and at the canonical API.

## Validation and remaining acceptance

`frontend/unit/setupAreas.spec.ts` verifies twelve unique areas, unique destination IDs, internal allowlisted paths, unknown-area fallback, any-of route access, restrictions, loading/error/disabled distinctions, pathname-only module lookup, operation classification, existing shift settings, and company-scoped group restrictions. Run `env -u NO_COLOR npm run test:unit` and `npx tsc --noEmit` from `frontend`.

Remaining integration acceptance: preserve editor-level guards, render the area navigator, verify each manual route with actual authorized personas and enabled/disabled flags, test company/tenant boundaries through direct APIs, and prove manual/document drafts reach the same canonical persistence workflow. A source-inspected form, a visited area, a flag or a successful catalogue unit test is not evidence of configured, deployed or owner-accepted behavior.
